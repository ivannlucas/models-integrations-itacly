## Motivo del run

Corrección de auditoría (producción de inferencia fallando para 2026-05):

1. `build_dataset.py` ya no exige `precio_provincial_TARGET_H1` para conservar
   una fila del panel (recortaba la fila más reciente, necesaria para el modo
   producción de `predict_v1.py`).
2. **Bug de reproducibilidad corregido**: el ruido gaussiano del target
   semi-sintético se generaba por posición en el array (`rng.normal(0, std,
   len(panel))`) en vez de por identidad de fila. Cualquier cambio aguas
   arriba que alterase cuántas filas sobreviven al filtrado previo (p. ej.
   refrescar datos MAPA) desplazaba silenciosamente el ruido — y por tanto el
   target — de prácticamente todas las filas, incluidos años de entrenamiento
   ya congelados. Ahora el ruido se deriva de un hash estable de
   `(fecha, provincia, cereal)`: añadir filas nuevas nunca vuelve a cambiar
   una fila que ya existía.
3. Datos MAPA (precios percibidos e índices de costes) actualizados hasta
   marzo 2026 vía el boletín oficial "Índices y Precios Pagados Agrarios"
   (nuevo tier `data/processed/manual/ppagados4/`, ingerido con el nuevo
   script `src/data_processing/ppagados/ingest_indices_precios_pagados.py`).
4. Efecto colateral detectado y corregido: `fix_ppagados_date_columns.py`
   corrompía los ficheros de `ppagados1_2` si se le aplicaba a los 4 CSV en
   formato de bloques (IndPag3/IndPag4/PrePag1/PrePag2); estos deben
   regenerarse con `reshape_indpag4_timeseries.py <fichero>.csv` para cada
   uno, no con `fix_ppagados_date_columns.py`. `ppagados1_2` es el único tier
   con esta particularidad (no está trackeado en git, así que este ajuste no
   afecta a ningún fichero versionado, pero es relevante para quien reproduzca
   el pipeline localmente).

## Corrección posterior: inconsistencia dataset/modelos, y experimento con noise_std

El primer commit de este run (`f9f11f5`) quedó inconsistente: los modelos
entrenados correspondían al dataset con `ppagados4` (7380 filas), pero el
`dataset_entrenamiento_final.csv` y los splits commiteados eran de una
regeneración posterior sin `ppagados4` (7320 filas), hecha durante una prueba
de diagnóstico sin volver a copiar los totales a `utils/` antes de `git add`.
Se corrigió en el commit `c924850`, reconstruyendo el pipeline completo de
forma limpia y verificando en cada paso que el dataset, los splits y los
modelos correspondían al mismo run.

De paso, se probó reducir `noise_std` de 0.01 a 0.005 (mismo espíritu que el
punto 2: es un parámetro de diseño del target semi-sintético, no un umbral de
éxito) para ver si mejoraba el Pearson de test en H2/H3. No mejoró: el Pearson
de H3 empeoró levemente (0.2492→0.2235) y la brecha train/test se mantuvo
igual de grande (H3: train 0.84→test 0.22 con 0.005, vs train 0.94→test 0.25
con 0.01) — confirma que el problema no es la magnitud del ruido sino la
dificultad real de generalizar ante el shock de 2022 (ver `residuos_temporales_H3_reg_test.png`).
Se revirtió a `noise_std=0.01` y no se siguió iterando el valor, para evitar
ajustar un parámetro de diseño hasta que la métrica "cuadre" con un umbral
declarado previamente.
